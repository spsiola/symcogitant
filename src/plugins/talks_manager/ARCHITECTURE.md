# Универсальный менеджер диалогов (TalksManager)

## Цель и концепция
`TalksManager` — это центральное ядро управления общением ИИ-агента. Он абстрагирует протоколы связи (Telegram, Discord, Web-чат) и представляет любой чат как универсальную сущность **"Разговор" (Talk / Room)**.

Эта архитектура позволяет отвязать бизнес-логику агента, формирование контекста и управление памятью от специфики конкретных мессенджеров. Транспорты (адаптеры платформ) занимаются только I/O (прием-передача), а `TalksManager` управляет правилами и смыслом.

## 1. Архитектурные слои

### 1.1 Транспортный слой (Adapters)
Транспорты (например, `TelegramTransportPlugin`) служат мостом между платформой и ядром.
**Обязанности транспорта:**
*   Регистрировать в `TalksManager` свои **Возможности (Capabilities/Tools)**: умеет ли он редактировать сообщения, удалять, ставить реакции, присылать медиа.
*   Регистрировать свою **Идентичность (Identity)**: от чьего имени работает этот транспорт (ID/ник в Telegram, почтовый адрес для e-mail, или имя из `soul.json` для веб-интерфейса). Это нужно, чтобы `Talk` понимал, какие сообщения в истории "свои", а какие "чужие".
*   Регистрировать **События (Events)**, которые он может отслеживать (входящие сообщения, изменения, удаления).
*   Транслировать платформозависимые события в **Универсальные события** (`talk_message_received`, `talk_message_deleted`).
*   Выполнять приказы от `TalksManager` (отправить текст, поставить реакцию), полученные через универсальную шину событий.

### 1.2 Ядро (TalksManagerPlugin)
Управляет коллекцией активных `Talk` (комнат).
*   Поднимает в память объект комнаты, если получено событие с новым `talk_id` (формат: `протокол:тип:ID`, например `tg:priv:12345` или `tg:forum:100555:topic:42`).
*   Служит реестром зарегистрированных транспортов, их Capabilities и Identities.
*   Маршрутизирует универсальные события в нужную комнату.
*   Сохраняет состояние всех комнат (диалогов) в изолированных папках по пути `data/talks/<protocol>/<room_id>/` (файлы `profile.json`, `history.jsonl`, `state.json`).

### 1.3 Универсальная комната (Talk)
Инкапсулирует состояние конкретного диалога. Особенности реализации:
*   **Темы и Форумы (Topics):** Если транспорт поддерживает темы (как Telegram Forums), каждая тема является полностью изолированным объектом `Talk`. Агент никогда не перепутает контекст разных тем одной группы.
*   **Умная История (Smart History):** Ведение append-only журнала в JSONL. В историю записывается не только текст, но и хронология действий: кто и когда поставил реакцию, кто удалил сообщение. Для LLM это форматируется в виде детального "скрипта пьесы" с таймстемпами, так же в пьессу пишется когда модель читала разговор. Синхронизация с сервером записывает diff, сохраняя локальные мысли агента.
*   **Профили и Режимы (Profiles):** Как в `Praxis`, комната имеет метаданные и статусы (`private`, `public`, `important`, `frozen`, `observer`).
*   **Настройки поведения (Settings):** Для каждой комнаты задаются конфигурации:
    *   Пожелания к LLM (какую модель использовать — легкую/продвинутую, размер контекста).
    *   Триггеры (по каким конкретным событиям дергается LLM — на каждое сообщение, только на reply, при упоминании).
    *   Регулярное чтение: как часто LLM "читает" новые сообщения в фоне, даже без явных триггеров.
*   **Надежность и Идемпотентность (Outbox):** `Talk` реализует паттерн надежной очереди исходящих сообщений. Если во время генерации длинного ответа сервер упадет, система гарантирует, что сообщение будет доотправлено при старте без создания дубликатов.
*   **Медиа-ассеты:** Если транспорт передал маркер `[Голосовое сообщение, 14 с]`, комната может через инструменты LLM явно запросить файл для транскрибации (STT).
*   **Участники:** Ведение абстрактного списка участников (ростер, роли).

### 1.4 LLM Layer (Слой модели)
В этой архитектуре LLM рассматривается как специализированный "внутренний участник". `Talk` готовит для LLM:
*   Оптимизированный контекст (с учетом окон токенов и лимитов модели).
*   Список доступных **Инструментов чата** (формируется на лету из Capabilities транспорта):
    *   Ответить (`reply`)
    *   Отредактировать своё прошлое сообщение (`edit_message`)
    *   Промолчать/Пропустить (`ignore`)
    *   Запросить скачивание/парсинг медиа из истории (`request_media`)
    *   Запросить более глубокую историю (`request_more_history`)
    *   Поставить реакцию/эмодзи (`set_reaction`)

## 2. Формат универсального события (UniversalMessage)

Каждое сообщение или действие приводится к стандарту:
```json
{
  "talk_id": "tg:group:-100555:topic:42",
  "msg_id": "1004",
  "protocol": "telegram",
  "date": "2026-10-02T12:00:00+00:00",
  "sender": {
    "id": "428611700",
    "name": "Sergei Σψ",
    "role": "user"
  },
  "text": "Посмотри этот файл",
  "attachments": [
    {"type": "document", "file_id": "file_123", "mime": "application/pdf"}
  ],
  "reactions": [],
  "is_outgoing": false,
  "is_deleted": false
}
```
