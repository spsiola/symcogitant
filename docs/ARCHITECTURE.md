# Архитектура проекта Symcogitant

Этот документ описывает высокоуровневую архитектуру ИИ-сущности Symcogitant.

ИИ-сущность Symcogitant представляет собой мультимодальную и мультисессионную систему, объединенную через:
- общее состояние запущенного инстанса - весь набор работающих процессов, временных файлов
- общий промпт-идентичности, который инжектится во все контексты при общении с ЛЛМ
- общую память, из которой собираются контексты для "думания" с ЛЛМ каждый раз своим способом, в зависимости от процесса думания
- общие секреты харнесс
- общий харнесс, включающий в себя набор инструментов, набор приборов, набор скилов, набор mcp-сервисов и source code со всей его git историей


symcogitant.py - входная точка в систему, минимальный файл, который разворачивает "жизненный метаболизм":
- запускает демоны (Daemons) - фоновые процессы, watchdog'и и контроллеры жизнедеятельности (мониторинг, логирование).
- цикл "сознания" - сессия с ЛЛМ, по временному "тику" и по событиями (обдумать) дергает ЛЛМ, с промптом из текущих события "жизнидеятельности", "лампочек" и "шкал" приборов, состояний прочих "думательных" процессов. Задача - контроль бюджета разных ЛЛМ, частота "тиков" разных "думащих процессов", инициация "думающих" процессов, подтверждение запросов на завершение думающих процессов.
- плагины-сенсоры (чисто питоновские скрипты) обеспечивают циклы коммуникации с различными средами: веб-интерфейс, телеграм, дискорд, и др - отслеживание новой инормации типа "мне написали", "обновился чатик" и запуск отдельных думающих субпроцессов с ЛЛМ (через воркеры) типа "коммуникация в канале" - личное общение, общение в группе.

## 2. Основные компоненты (v0.5.0)

### Архитектура исполняемых модулей (Base Classes)
- **`BaseModule`** (`src/core/base.py`): Абстрактный базовый класс для всех исполняемых компонентов. Отвечает за инициализацию, запуск/остановку, статусы и отправку логов.

Система модулей строго разделена по зонам ответственности (по "кто, где и для чего"):

1. **Plugins (Плагины - Сенсоры и Когнитивные функции)**
   - **Назначение:** Интерфейсы взаимодействия и маршрутизация. Это «глаза», «уши» и «язык» агента. Плагины общаются с внешним миром (веб-интерфейс, Telegram) и диспетчеризируют события.
   - **Расположение:** `src/plugins/` (встроенные) и `data/plugins/` (приватные, ИИ-сгенерированные).
   - **Класс:** `BasePlugin`.

2. **Daemons (Демоны)**
   - **Назначение:** Постоянные фоновые процессы. Бесконечный цикл работы, поддержание гомеостаза. Это «внутренние органы» (например, мониторинг системных ресурсов, сбор метрик).
   - **Расположение:** `src/daemons/` и `data/daemons/`.
   - **Класс:** `BaseDaemon`.

3. **Workers (Воркеры)**
   - **Назначение:** Выполнение работы по требованию (по событию). Воркер "просыпается", отрабатывает задачу и "засыпает". В основном это коннекторы к тяжелым вычислительным ресурсам (например, вызовы LLM).
   - **Расположение:** `src/workers/` и `data/workers/`.
   - **Класс:** `BaseWorker`.

4. **Interceptors (Интерцепторы / Пре-Пост-процессоры)**
   - **Назначение:** Алгоритмическая обработка (middleware) пайплайнов. Это фильтры, которые стоят между другими компонентами (например, SecurityInterceptor для проверки безопасности вызовов и контроля утечек данных/DLP).
   - **Расположение:** `src/interceptors/` и `data/interceptors/`.
   - **Класс:** `BaseInterceptor`.

### Инструменты и Расширения знаний агента
1. **Tools (Инструменты)**
   - **Назначение:** Набор функций (Function Calling), доступных LLM по стандартам OpenAI/Hermes. 
   - **Расположение:** `src/tools/` и `data/tools/`. Инструменты автоматически сканируются `ToolsRegistry`, который генерирует для них JSON Schema.
2. **Skills (Навыки)**
   - **Назначение:** Стандартные знания и инструкции для агента (например, Markdown-файлы с алгоритмами, инструкциями, скриптами).
   - **Расположение:** `src/skills/` и `data/skills/`.
3. **MCP Servers (Model Context Protocol)**
   - **Назначение:** Стандарт для подключения внешних инструментов и источников данных. Ядро динамически подключается к MCP-серверам и регистрирует их инструменты в `ToolsRegistry`.

## Component Communication
- **Event Bus Pattern** (`src/core/event_bus.py`): Все компоненты общаются друг с другом посредством передачи JSON-сообщений через центральный `EventBus`. Это обеспечивает слабую связность (loose coupling) и асинхронную обработку. Шина также поддерживает **Interceptors (Middleware Chain)**: перед доставкой подписчикам событие проходит через зарегистрированные фильтры, которые могут модифицировать или заблокировать его (например, DLP защита).
- **Core Registry (Dependency Injection)**: Для мгновенного доступа к синхронным, статичным или закешированным данным, ядро `SymcogitantCore` прокидывает ссылку на себя во все модули (`self.core`). Модули могут использовать `core.get_plugin(name)`, `core.get_daemon(name)` или `core.get_worker(name)` для получения ссылок напрямую. Этот подход используется там, где задержки EventBus недопустимы.
- **`config.yaml`**: Централизованная конфигурация системы с отдельными секциями: `plugins`, `daemons`, `workers`, `interceptors`, `mcp_servers`.

## Текущие встроенные модули
### Плагины (Сенсоры / Роутеры)
- **WebInterfacePlugin (`src/plugins/web_interface`)**: Асинхронный веб-сервер на базе FastAPI + Uvicorn, предоставляющий UI для мониторинга. Подписывается на `EventBus` и транслирует все события типа `log` через WebSockets подключенным клиентам в режиме реального времени. Интерфейс реализован с использованием Vanilla JS/CSS (Dark Mode, Glassmorphism). Принимает сырые RAW JSON события и рисует их в консоли отладки.
- **TelegramTransportPlugin (`src/plugins/telegram_transport`)**: Чистый адаптер связи с Telegram от имени пользователя (MTProto / Telethon). Регистрирует свои возможности (отправка, удаление, реакции) в TalksManager. Транслирует платформозависимые события в универсальные события EventBus и выполняет обратные команды.
- **TalksManagerPlugin (`src/plugins/talks_manager`)**: Универсальное ядро управления общением. Абстрагирует любой чат до сущности `Talk` (комнаты). Изолирует данные каждого диалога в отдельной папке `data/talks/<protocol>/<room_id>/` (содержит `history.jsonl`, `profile.json`, `state.json`). Отвечает за ведение умной истории в формате "сценария пьесы", буферизацию сообщений, триггеры и формирование контекста для вызова LLM.

### Демоны (Фоновые процессы)
- **FileLoggerDaemon (`src/daemons/file_logger`)**: Глобальный перехватчик событий. Собирает все сообщения из `EventBus` и сериализует их в строгий формат JSONL с привязкой по источнику (`source`) для системного системного логирования работы модулей.
- **SystemMonitorDaemon (`src/daemons/system_monitor`)**: Сбор метрик (CPU, RAM) и 3-уровневый опрос реестра LLM провайдеров (пинг доступности локальных и облачных моделей).
- **MCPManagerDaemon**: Управление внешними инструментами по стандарту Model Context Protocol.

### Воркеры (Исполнители)
- **ModelSelectorWorker (`src/workers/model_selector`)**: Динамический маршрутизатор LLM моделей. Поддерживает логику `Smart Quarantine` (временная блокировка моделей при ошибках 429/503) и `Cache Affinity` (удержание одной и той же модели в рамках одного диалога для экономии KV-кэша). Выдает оптимальную модель для каждого запроса, поддерживая проброс конкретных ключей (`модель#ключ`).
- **LLMWorker (`src/workers/llm_worker`)**: Исполнитель запросов к LLM (OpenAI, Anthropic и др.). Поддерживает tool calling, динамический выбор API-ключей (переданных от ModelSelectorWorker) и учет затраченных токенов (биллинг).
- **ToolWorker (`src/workers/tool_worker`)**: Изолированное выполнение инструментов (tools) и скриптов (`run_command`), запрошенных через LLM.
- **ContextAssemblerWorker (`src/workers/context_assembler`)**: Сборка и форматирование контекста для LLM на основе декларативной схемы (`ContextSchema`). Применяет лимиты окна, склеивает системные промпты из файлов, расставляет теги кэширования (Prompt Caching) и фильтрует доступные инструменты.
